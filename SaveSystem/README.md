# Save System

**프로젝트**: 파파라치 (개인 프로젝트)
**역할**: 설계 및 전체 구현

게임 진행 구조에 맞춰 필요한 범위만 저장하도록 단순화한 세이브 시스템입니다.
3개의 독립 슬롯 구조와 정산 시점 한정 저장 방식을 통해 세이브 데이터의 복잡도와 크기를 최소화하도록 설계했습니다.

---

## 데이터 구조

### SaveData

단일 세이브 슬롯에 대한 데이터 구조체입니다.
게임 복원을 위한 최소한의 데이터만 저장하도록 구성했습니다.

| 필드 | 설명 |
|------|------|
| `DayCount` | 현재 진행 일수 |
| `HasMoney` | 보유 금액 |
| `RequesterPoints[]` | 진영별 신뢰도 (배열) |
| `LastTimeToString` | 마지막 저장 시점 (슬롯 UI 표시용) |

### GlobalSaveData

세이브 슬롯 전체(3개)와 마지막 세이브 이어하기 편의성을 제공하기 위한 데이터입니다.

**슬롯을 다중으로 설정한 이유**

게임 진행 중 진영별 신뢰도에 따라 분기가 발생합니다. 단일 세이브라면 특정 분기 진입 후 다른 분기를 확인하려면 기존 데이터를 초기화해야 하는 문제가 생깁니다. 이를 해결하기 위해 세이브 데이터를 독립적인 슬롯 단위로 분리했습니다.

- 분기별 진행 상태 유지
- 재플레이 및 테스트 편의성 향상

---

## 세이브 시점

```
일과 시작 → 플레이 진행 → 일과 정산 → [데이터 저장] → 다음날로 이동
```

저장은 **일과 정산 종료 시점에만** 수행하도록 설계했습니다.

**이 시점을 선택한 이유**

정산 단계에서는 플레이 진행의 결과가 확정되어 게임 상태가 안정화된 시점입니다.
저장 시점을 이 단계로 제한함으로써 다음 효과를 얻을 수 있습니다.

- 불필요한 저장 호출 감소 (세이브 구성에서 변화하는 데이터는 정산에서만 발생)
- 세이브 데이터 크기 최소화 (플레이 진행 중 저장 시 맵 상태 및 런타임 오브젝트 상태를 추가 저장해야 하므로 복잡도 증가)

---

## 설계 판단

플레이 중 비정상 종료에 대응하기 위해 진행 상태 전체를 저장하는 방식도 고려했으나, 현재 게임 구조에서는 정산 단계 이후에만 상태가 확정되므로 저장 시점을 제한하는 것이 세이브 구조의 복잡도와 관리 측면에서 더 적절하다고 판단했습니다.

세이브 데이터를 핵심 상태만 포함한 최소 구성으로 유지하여, 추후 시스템 변경이나 기능 확장 시 저장 데이터 의존도를 낮추는 것을 우선했습니다.
